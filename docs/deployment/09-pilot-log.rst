What we actually did — the pilot deployment log
================================================

The previous pages describe the *clean* path. This page is the honest record of the real one: every command
that was run, every mistake, every detour, in order, with what each one taught us. It is written so that
someone repeating the exercise recognises each bump when they hit it. Times are Pacific unless marked UTC.

Day 1 — Monday 7 September: preparation and the first attempts
--------------------------------------------------------------

**Ports.** Console → Networking → VCN ``vcn-20260505-0014`` → Default Security List → *Add Ingress Rules*:
two rules, ``0.0.0.0/0`` TCP 80 (HTTP) and TCP 443 (HTTPS). The second rule was accidentally described as
"HTTP" too — cosmetic, ignored. Result: five ingress rules (22, two ICMP defaults, 80, 443).

**First A1 attempt, by hand.** Compute → Create instance, ``VM.Standard.A1.Flex`` 1 OCPU / 6 GB, Ubuntu 24.04,
SSH key generated by the console and downloaded as ``ssh-key-2026-09-08.key`` / ``.pub``. Result in AD-1:
*Out of capacity for shape VM.Standard.A1.Flex*. Same in AD-3, then AD-2.

**OCI CLI on the Mac** (``brew install oci-cli jq``, ``oci setup config``). This took several rounds:

* an older API key and config from May did not match (``NotAuthenticated``);
* a new key generated from the console (*My profile → API keys → Generate API key pair*) with the
  "Configuration file preview" pasted into ``~/.oci/config`` and ``key_file`` pointed at the downloaded
  ``…private.pem`` (Oracle names it ``…Z.pem``, so a ``*private.pem`` glob did not match);
* still ``NotAuthenticated`` for a couple of minutes — key propagation — then ``oci iam region list`` worked.

**SSH key housekeeping.** ``~/.ssh`` had no keys at all; the console-generated pair was copied from
``~/Desktop/codebase/oracle_keys/sharpen/`` to ``~/.ssh/sharpen_vm`` and ``.pub``, ``chmod 600``.

**Retry script, first version** (``deploy/oci-retry-a1.sh``), run on the Mac with
``SSH_PUB=~/.ssh/sharpen_vm.pub caffeinate -i bash deploy/oci-retry-a1.sh``. Bugs found by running it:
``mapfile`` does not exist in macOS bash 3 (replaced by a ``while read`` loop); the image filter excluded
``aarch64`` instead of selecting it; ``oci iam availability-domain list`` returned 401 with the fresh key,
so a fallback derives the AD names from an existing instance's AD (``RUzw:US-ASHBURN-AD-1..3``).

20:34 — first automated attempt. ``out of capacity`` in all three ADs, every two minutes.

20:43 — the script **quit** on a network timeout (*The connection to endpoint timed out*), because any
non-capacity error was treated as fatal. Fix: timeouts, ``TooManyRequests``, ``ServiceUnavailable`` and 5xx
are now "transient" — wait 30 s and continue; only after 10 in a row does it give up.

Overnight — the Mac was closed. ``caffeinate -i`` prevents idle sleep, not lid sleep: between 23:23 and
09:54 the script made **two** attempts. The best capacity window was missed. Lesson: run the hunter on a
machine that never sleeps.

Day 2 — Tuesday 8 September: moving the hunt, and everything around it
----------------------------------------------------------------------

**Sizes.** The script was changed to rotate through ``1:6 2:12 4:24`` (OCPU:GB) in each AD, on the theory
that Oracle frees capacity in uneven chunks. Copying the updated file into the project was missed twice
(the old script kept running without sizes in its log lines) — confirmed by the absence of ``1 OCPU/6 GB``
on the attempt lines.

**Hunter moved to the always-on bot VM.** Steps that went wrong first:

* ``scp … <user>@<bot-ip>:~`` was pasted with the placeholders literally → ``zsh: parse error``.
* ``ubuntu@`` with the default key → *Permission denied (publickey)*; the bot VM uses a different key. Found
  by ``ls -R ~/Desktop/codebase/oracle_keys/``: ``ssh-key-2026-05-05 (1).key`` (the space and parentheses
  need quotes: ``K="$HOME/Desktop/codebase/oracle_keys/ssh-key-2026-05-05 (1).key"``).
* The VM-setup block was pasted while the ``ssh`` was still logging out, so it ran on the *Mac*: macOS
  ``sed`` failed (harmless), ``sudo apt-get`` asked for a Mac password (Ctrl+C). Lesson: paste server
  commands only after the prompt reads ``ubuntu@instance-…:~$``.

On the VM: ``sed`` the ``key_file`` path in ``~/.oci/config``; ``apt-get install jq python3-venv``
(Ubuntu's purple *Pending kernel upgrade* and *Which services should be restarted?* screens — Tab to
``<Ok>``, Enter); ``python3 -m venv ~/ocienv && ~/ocienv/bin/pip install oci-cli`` (several silent minutes
on the Micro); ``oci iam region list`` printed JSON. Then
``SIZES="1:6 2:12" SSH_PUB=~/sharpen_vm.pub nohup bash ~/oci-retry-a1.sh > ~/retry.log 2>&1 &``.

18:26 UTC — attempt 3, ``4 OCPU/24 GB`` → **LimitExceeded**, and the script quit (not a capacity error).
Diagnosis with ``oci limits resource-availability get --limit-name standard-a1-core-count``: the tenancy's
A1 quota is **2 cores per AD**, not the advertised 4; no stray instance existed. Fix: ``LimitExceeded`` now
drops that size from the rotation and continues. Restarted with ``SIZES="1:6 2:12"``.

**DuckDNS.** Signed in with Google, added ``sharpen-ai`` → ``sharpen-ai.duckdns.org``. The page auto-filled
the laptop's IP; ignored.

**deploy/.env.** ``DOMAIN=sharpen-ai.duckdns.org``; the hand-typed password replaced by
``openssl rand -base64 24 | tr -d '/+='``; ``ADMIN_EMAIL`` and ``DEMO_DATA=false``. Confirmed ``git status``
does not list it.

**GitHub.** Repository public, README rendering, latest commit present — the VM will be able to clone
without a token.

**Docs and hygiene.** The deployment chapter (pages 1–6) was written; a review of it found partial real
values (8 characters of the DB password and of the DuckDNS token, the API-key fingerprint, the bot VM's IP,
local key paths) — all replaced with placeholders before commit. ``private/`` was created for a credentials
document (Markdown + PDF, ``make-pdf.py``) and git-ignored. ``docs/for-companies.rst`` and the README's
*About this project* section were added.

**CI/CD.** ``ci.yml`` gained a docs job; ``deploy.yml`` (image to GHCR, SSH rollout with health check and
rollback, skipped until secrets exist), ``codeql.yml``, ``release.yml``, ``dependabot.yml``,
``deploy/Dockerfile.ci``, ``deploy/remote-deploy.sh`` were added. ``actionlint`` caught one real error:
``secrets.*`` is not allowed in a step-level ``if`` — moved into a job ``env`` and tested there.

Day 3 — Wednesday 9 September: the pipeline goes live, and Plan B
-----------------------------------------------------------------

**Pushed straight to main** (the ruleset did not exist yet): commit "CICD pipeline". GitHub ran CI (green),
then **Deploy #1** (2 min 8 s): built the arm64+amd64 image, pushed
``ghcr.io/bhushanladde02/sharpen:<sha>`` and ``:latest``, and skipped the rollout with the summary
*Production VM not configured yet*. CodeQL ran. Dependabot immediately opened nine PRs, each with green CI.
The GHCR package came out **public** automatically (public repository) with *Inherit access from source
repository* on — nothing to change.

**Ruleset** ``protect-main`` created: Active; bypass *Repository admin*; target *Default branch*; restrict
deletions; block force pushes; require a pull request (0 approvals); require status checks *Build and test*,
*Boot and serve*, *Documentation builds cleanly* with branches up to date. One duplicate "Build and test
(Any source)" row was removed before saving — a duplicate would leave PRs waiting forever for a second
check that never reports.

**The A1 verdict.** By 18:42 UTC the hunter had made **671 attempts** across three ADs and two sizes over
~24 hours with nothing but ``out of capacity``. Options weighed: keep waiting; upgrade the account to
Pay-As-You-Go (reportedly unblocks A1, but removes the cannot-be-billed guarantee); or launch on the other
free shape. Decision: **Plan B — the 1 GB E2.1.Micro**, with the hunter left running for a later migration.

**Plan B, executed.**

#. ``deploy/oci-create-micro.sh``, ``deploy/docker-compose.micro.yml`` (JVM 320 MB heap, serial GC, C1-only
   JIT; PostgreSQL 32 MB shared buffers), swap creation in ``setup-vm.sh``, ``SMALL_VM`` handling in
   ``remote-deploy.sh``, and page :doc:`08-small-vm` were written. ``SMALL_VM=true`` appended to ``.env``.
#. First change through the new PR flow: branch ``micro-plan-b`` → PR #10 → CI + CodeQL green (about 3
   minutes; the Maven cache makes *Build and test* ~30 s) → merged as ``b4ee3fc``, "9 checks passed".
#. 11:50 — ``SSH_PUB=~/.ssh/sharpen_vm.pub bash deploy/oci-create-micro.sh``:
   image ``Canonical-Ubuntu-24.04-2026.08.25-0``, **CREATED in AD-1 on the first try**, instance
   ``sharpen-micro``, **Public IP 150.136.83.28**.
#. DuckDNS: the IP was first typed into the **ipv6** box by mistake. Corrected: ipv6 emptied, IP into
   *current ip*, *update ip* → *success: ip address for sharpen-ai.duckdns.org updated to 150.136.83.28*.
   ``dig +short sharpen-ai.duckdns.org`` on the Mac → ``150.136.83.28``.
#. *(next)* ``ssh -i ~/.ssh/sharpen_vm ubuntu@150.136.83.28`` → ``setup-vm.sh`` from ``main`` (adds the 2 GB
   swap) → clone → ``scp`` the ``.env`` → ``APP_IMAGE=ghcr.io/bhushanladde02/sharpen:latest bash
   deploy/remote-deploy.sh`` → register the admin account → turn on the pipeline's deploy stage
   (:doc:`07-ci-cd`, "Turning the deploy stage on").

Things to remember from this log
--------------------------------

* Oracle's free ARM pool in Ashburn can be unavailable for days; the Micro is available in seconds.
* A Free Tier tenancy may have an A1 quota of 2 cores, not 4 — check *Limits* before assuming.
* Run anything that must poll for hours on a machine that does not sleep.
* Paste server commands only when the prompt says you are on the server.
* Placeholders in angle brackets are for you to replace; the shell will not do it.
* DuckDNS has two boxes per row; the IPv4 one is *current ip*.
* Screenshots leak: the DuckDNS token appeared in two of them and should be regenerated.
* A required status check listed twice blocks every PR.
* The first push to ``main`` without a ruleset is fine; the ruleset applies from the moment it is created.
